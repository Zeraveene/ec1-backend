# EC1 whole-save and grant contract

The Unity serializers inspected are `SaveData.ToJson`, `GameDataManager`, `PlayerAttributes`, `InventoryManager.SaveInventoryData`, `PlayerConsumable`, and `EpiconAchievements.SaveAchievementData`. Synthetic character fixtures in `tests/fixtures` are copied from EC1's shipped `Assets/Resources/{alaster,edna}base.txt`. `tests/fixtures/unity-fresh-save.json` is the real shipped prefab/resource profile exported by the Unity Editor with 99 fields. No player exports are included. `src/game/item-catalog.json` contains 41 static material/consumable Item assets exported through `AssetDatabase`/`JsonUtility` from the game, not from player preferences.

All game routes are mounted under `/api/game`. Except `/migration/proof`, they require an EC1 bearer session and current ban checks. Identity comes from the session; body player IDs have no authority. A migration scope can access only readiness and migration operations.

## Snapshot

`PUT /save` accepts `{game:"ec1",schemaVersion:1,playtime,data,expectedSaveVersion,operationId,deviceId?,intent?}`. `data` is a dictionary of strings. `data.CLOUD_ALL_DATA` is the JSON string of the complete EC1 preference dictionary; `data.Playtime` preserves the captured legacy clock. For an intentionally default first profile use `intent:"new_game"`. Unknown preference and envelope-data fields and explicit zero/empty string values survive publication. Credentials, PF/GPGS/backend credential keys, password/token/secret keys are forbidden, including envelope fields. Duplicate JSON property names are rejected so server-accepted profiles can decode through the native Unity codec. Maximum serialized data is 2,000,000 UTF8 bytes; request bodies are bounded at 2,100,000 bytes.

The native required set is exported as `nativeKeys` in `src/game/validation.ts`: the historical 60 keys plus 30 supplemental integer keys, six string keys and three float keys, total 99. This closes the original serializer's missing `elysianTaken`, quest task/progress, tutorials, companion settings, step-up offers, costume selection/transmog, daily reset, boosters and local clock. Legacy imports validate the historical 60 keys without fabricating newly introduced entitlements or preferences. Completeness requires key presence; locked characters may legitimately have empty attribute strings.

`gamedata` is a JSON object with nonnegative finite gold/ruby/stageProgress/tutorialProgress/timeCounter and usedCoupons/stageInfo arrays. Character JSON must contain level/exp and four serialized equipment strings. Inventory is the actual EC1 format: three `^` separated groups, each containing `|` separated JSON item objects; initialized empty inventory is `^^`. Consumable is optional empty legacy data or a JSON object. `achievements_new` is empty legacy data or exactly 27 `0|1` flags, **not JSON**. Supplemental integers use signed Int32 bounds; supplemental floats are finite strings.

`GET /save` and successful publication return `{playerId,saveVersion,playtime,data,saveState,operationId}`. No initial snapshot is an expected `404 {error:"no_save",saveState:"native_uninitialized",saveVersion:0}`. `409 save_conflict` means fetch/reconcile while retaining the journal; an operation ID reused with changed bytes/options is `409 operation_id_reused`. Replaying the identical operation returns its exact committed revision, even after later saves. Clients must retain newer dirty local progress instead of blindly importing an older acknowledgment. A same-account save cannot decrease published playtime. Native default/reset uploads cannot replace a revision with healthy progress merely by increasing the clock or retaining paid flags (`damaged_save_rejected`). Strong progress includes levels, stages/tutorials, positive inventory quantities/upgrades, earned statistics and achievement flags. Audited admin restoration opts into decrease explicitly and uses the same publication primitive.

Publication writes immutable uniquely named R2 bytes, verifies readback SHA256, then atomically batches D1 revision/operation insertion and a conditional `player.save_version` update. Failed staging never changes the published head. Concurrent writers cannot both publish the same expected version. Unreferenced staged objects are retained for later audited retention handling; no destructive cleanup is included. `save_revision` is the immutable history, and `save_operation` is the exact-retry index. R2 integrity/missing objects fail typed; they do not become empty/new saves.

## Mail, daily and coupons

- `GET /inbox` returns `{mail:[{id,title,body,rewards,createdAt,expiresAt,readAt,claimedAt}]}` (latest 100 unexpired rows).
- `POST /mail/:id/read` returns `{read:true}` and does not claim anything.
- `POST /mail/:id/claim` accepts `{operationId,expectedSaveVersion}` and returns the whole resulting save.
- `GET /time` returns epoch milliseconds `serverTime` and ISO `isoTime`.
- `GET /daily/check` returns `{claimCount,lastClaimAt,nextEligibleAt,eligible,serverTime}` in epoch milliseconds. Attendance retains EC1's elapsed 24-hour rule.
- `POST /daily/claim` accepts `{operationId,expectedSaveVersion}`. Configure `game_config` key `daily_rewards` as `{rewards:[[{id:"gold",amount:100}],...]}`. An unconfigured table is `503 daily_not_configured`. The grant updates LastReward/LastRewardTime and publishes before receipt completion. Daily quest/challenge/booster refresh remains a separate client integration gate; this endpoint does not silently infer those reward/reset codecs.
- `POST /coupon/redeem` accepts `{code,operationId,expectedSaveVersion}`. `coupon` rows must be enabled and unexpired. Case-sensitive codes are 1-64 ASCII letters/digits/underscore/hyphen. The grant updates `gamedata.usedCoupons` and durable redemption together.

Rewards have EC1-compatible `{id,amount,name?,itemCategory?}` shapes. Supported: `gold`, `ruby`, known `costume_{character}_{1..8}` flags, and the 41 shipped material/consume IDs in the catalog. Material category is 1 and consume category is 2, matching EC1 `ItemCategory`. The backend infers the catalog category and rejects mismatches; canonical Item metadata supplies new inventory entries and overwrites known metadata of the affected stack while preserving valid unknown item fields. Asset sample quantities do not become player quantities. The grant adds to the existing player stack, respecting the actual asset stack bound. A full stack returns `409 reward_stack_overflow` with the source unclaimed, rather than silently dropping items. Currency earned counters update when present; balances stay within Int32. Equipment/randomized rewards and unknown IDs remain `422 reward_unsupported`; no claim/save is recorded on errors.

All receipts (`grant_receipt`) and mail claimed state publish in the same D1 transaction as the whole save. A lost reply with the same operation replays the original receipt/save. A different operation for an already granted source returns `409 {error:"reward_already_claimed",receipt:{playerId,saveVersion,operationId},latestSaveVersion}`; it deliberately contains no old snapshot data. Clients resolve the pending claim, fetch the current head and retain newer dirty local progress. Multiple claim attempts cannot duplicate the reward. A source can have only one receipt per player. Clients must import/reconcile the returned full save before subsequent uploads; gameplay inventory is still client authoritative and this milestone is not a server authoritative combat/economy implementation. Staging activation requires serialized journal uploads, menu-safe import and disabled old local grant callbacks; switching only login while leaving old claim paths active is insufficient.

## Profile and Fortress

`GET /profile` returns `{playerId,displayName}`. `PUT /profile {displayName}` trims/normalizes and accepts 1-24 characters without control characters or markup/delimiters; edits are bounded per player.

`GET /leaderboard?limit=100` returns `{leaderboard:"infinity_fortress",entries:[{playerId,playerName,score,saveVersion,rank}],me:{...}|null}`. Limit is 1-100. Each successful whole-save publication atomically attests a bounded FortressRecord score from `gamedata.fortress_alaster/edna/louisa/zerav`: `floor*1_000_000-cleartime*10+character`, matching EC1's enum and codec. Zero-floor records are uninitialized; active floor bounds are 1-2147, cleartime 0-99999 and scores Int32 positive. No arbitrary submitted score endpoint exists. Normal updates retain the highest attested record; explicit audited restoration recomputes it from the restored revision. Active bans exclude players from public ranking and protect requests. These are authenticated client save attestations, not proof of server-simulated combat or anti-cheat validation.

## Read-only migration

Migration defaults off (`LEGACY_MIGRATION_ENABLED` must equal `true`). New-account/save/grant operations make zero PlayFab calls. The adapter permits only explicit read/authentication endpoints and rejects all update/delete/marker/clear-mail/link/unlink/account-create operations before transport. Configuration/network failures cannot be interpreted as source absence.

`POST /migration/proof {sessionTicket,deviceId?}` revalidates the ticket with PlayFab `Server/AuthenticateSessionTicket`, obtains canonical legacy ID from the response, then reads `Server/GetUserAccountInfo`. It reserves/mints a 15-minute migration session for that canonical ID and stores server-owned `migration_identity_proof` with Google subject/email and a SHA256 CustomID hash. Device context is set only if supplied device ID exactly equals server CustomID. A submitted ID is never ownership proof. Long-term auth linking must additionally verify the same legacy Google subject or a read-only legacy email/password login; Discord/Apple cannot be arbitrarily attached by migration scope. Proof attempts are capped at 10 per trusted edge IP per five minutes before source transport; failed proof cannot create a player. Read-only PlayFab calls have a bounded ten-second timeout.

`POST /migration/import` uses a migration bearer session and `{sessionTicket,operationId,localSnapshot?}`. It revalidates source ownership and reads user data, inventory, profile and account info. Both originals are independently archived into immutable R2 and SHA256 checked before ranking. Source ticket/credentials are never included in archives. A local snapshot can compete only when `localSnapshot.deviceId`, verified session device context and current server CustomID agree. Legacy clients sometimes unlinked CustomID; those cases return `local_owner_mismatch` with preserved originals and require recovery rather than trusting a submitted local ID. Cryptographic local save signing did not exist in the old client; this proves legacy account/device provenance, not that gameplay bytes cannot be edited by their owner.

Sources with actual gameplay progress outrank default profiles that retained only paid flags, regardless of inflated clocks. Within the same health tier, validated sources rank by `gamedata.timeCounter`, with cloud winning ties. Separate high Playtime cannot make a reset/default source healthy. Strong progress includes upgraded characters, stages/tutorials, meaningful inventory, achievements and earned statistics. Low-progress legitimate paid accounts remain recoverable at a lower tier; standalone currency balances do not establish health. Known entitlement flags from independently validated same-account sources are retained as a union separate from the chosen gameplay timeline; gameplay fields are never merged. Missing/truncated/default sources cannot outrank healthy progress. Both damaged/default sources enter `migration_recovery_required`. Recovery holds retain archive references and a typed reason in `migration_record`. Nonempty PlayFab inventory/virtual currency requires `migration_entitlement_review_required` until its entitlement codec is reviewed; archived purchase/inventory evidence is never discarded or silently merged. Legacy ban evidence is archived, preserved in EC1's ban table and blocks import.

Pending `EC_MAIL_REWARDS` with supported reward shapes is imported into the native inbox with a deterministic source/player hash ID in the same atomic publication as the selected save. The source mail and all source fields remain unchanged. Empty mail is allowed. Unsupported/malformed rewards enter `migration_mail_review_required` with originals archived and no final claim/import. Native receipts prevent reimport/reclaim duplication; no PlayFab clear-mail callback exists.

The imported winner publishes as `imported_pending_auth`; `migration_record` tracks source archives/winner/version independently. Retries after commit return the actual committed save, never rerank or overwrite it. `/migration/complete` requires a normal player scope, an existing durable EC1 identity and a published imported snapshot, then sets migration complete/player migrated and revokes temporary migration sessions. Pausing new imports does not prevent an already imported player from finishing native authentication/cutover. Proof/import still fail while paused. `/readiness` separately reports nativeComplete and migration state. Source archive/save import alone is not native completion. Migration remains disabled for deployment until controlled legacy ownership/device/provider and entitlement tests pass.

SQL schema for admin integration is `migrations/002_game.sql`. Admin restores call exported `publishSnapshot`; all writers use the same CAS/R2 protocol. Admin audit rows publish atomically with restorations. Purchase module `020_purchases.sql` can add verified ledger/grant/paid-flag publication to the same transaction; existing server-owned paid flags are enforced on subsequent uploads before staging, with original request hashes retained for exact retries. Unsupported paid-flag keys fail typed. Save/grant/mail/config/migration-record timestamps use epoch milliseconds. Shared `player.created_at/updated_at/migrated_at` and authentication session/ban timestamps use epoch seconds. Initial synthetic staging rows written before this normalization may contain milliseconds in player.updated_at/migrated_at; no real player migration was activated, and source data is unaffected.
# Durable native device authentication

Real native guest creation securely persists a random `deviceCredentialId` (URL-safe 16–128 characters), random `deviceSecret` (URL-safe 43–128 characters, at least 256 random bits), and random installation `deviceId` before any request. Send all three alongside the existing guest bootstrap. The credential hash and canonical player are bound in the same D1 creation transaction. Bootstrap retries with changed device proof fail. Historical synthetic guest requests may omit the proof for compatibility; they do not acquire durable device sign-in automatically.

`POST /api/auth/device/login` accepts `{deviceCredentialId, deviceSecret, deviceId}` and returns ordinary native `AuthResult`. It never creates an account and remains available with new creation disabled or after the 30-day refresh family expires. Unknown ID returns `404 device_credentials_not_found`; wrong secret, wrong installation identity, or revoked credential returns `401 invalid_device_credentials`. Failures never invoke PlayFab. An unknown proof only permits retrying an already journaled original guest bootstrap at an explicit New Game boundary; ordinary sign-in must never become creation.

`POST /api/auth/link/device` accepts the same proof with a bearer session. Native players may register multiple installation credentials; credential IDs and secret hashes remain unique and cannot transfer ownership. Migration sessions may link only after a verified CustomID matching that session's original device identity has been stored by source proof and a snapshot has been durably imported for the same legacy player. The submitted native installation identity remains separate from the historical CustomID. No legacy identifier is a native secret.

An imported device-bound account can complete migration using its new native session. If linking succeeds but completion is interrupted, device sign-in returns `imported_pending_auth`; finish `/api/game/migration/complete` and read the authoritative save before gameplay. Completed migration revokes temporary source sessions. A known native credential prevents minting another migration session for that player.

Migration `021_device_credentials.sql` stores only hashes and epoch-second metadata. Device sessions reference their credential and authorization checks reject revoked credentials, including raced login sessions. Password recovery must atomically revoke every active device credential alongside sessions, retaining rows to prohibit reusing revoked identities. Explicit sign-out clears protected local proof; linking a durable email/provider remains necessary for recovery after device loss or sign-out. Never expose device secrets through logs, dashboards, save preferences, or unprotected journals.

# Native daily reset

`GET /api/game/daily/check` includes `reset: {period, eligible, nextEligibleAt, timezone: "UTC", serverTime}`. The period is the server's UTC epoch day (`floor(milliseconds / 86400000)`); local device time and timezone never select eligibility. Attendance reward claims retain their independent rolling 24-hour cooldown.

At a safe menu boundary, flush ordinary progress then journal `POST /api/game/daily/reset` with `{operationId, expectedSaveVersion, period}` using the returned period. The response is the ordinary complete `SaveResult`, published atomically with the unique account/period receipt `daily-reset:<period>`. Retry the exact request after response loss. A different operation for a completed period returns `reward_already_claimed` with canonical receipt metadata and the authoritative latest version, never an old save presented as current. Changed operation replay fields return `operation_id_reused`; stale period requests return `daily_reset_period_expired`. Preserve newer local gameplay if a reset acknowledgement arrives after another local checkpoint.

Reset selects three distinct EC1 QuestType values 0–11, clears quest progress/claims, sets treasure/march/chaos entries to 3 for premium or 2 otherwise, clears fox/golem/fairy hunger, and marks `dailyReset=1`. It preserves currency, progression, inventory, paid flags, buffs, attendance timestamps, and unknown fields. `dailyBoosterQuota="-1"` explicitly represents the historical absent/unactivated preference; Unity must delete that local preference on import and capture an absent preference as `-1`. Zero continues to mean an activated booster with no remaining charges. Other negative quota values are invalid.

A legacy profile whose `dailyReset=1` and parsed `LastRewardTime` are in the current UTC period does not reset its allowances again on first native contact. Subsequent eligibility uses immutable reset receipts. A backward server-clock adjustment cannot reopen an earlier period. This route never contacts or modifies PlayFab.
