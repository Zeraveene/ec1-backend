# EC1 whole-save and grant contract

The Unity serializers inspected are `SaveData.ToJson`, `GameDataManager`, `PlayerAttributes`, `InventoryManager.SaveInventoryData`, `PlayerConsumable`, and `EpiconAchievements.SaveAchievementData`. Synthetic character fixtures in `tests/fixtures` are copied from EC1's shipped `Assets/Resources/{alaster,edna}base.txt`; no player exports are included.

All game routes are mounted under `/api/game`. Except `/migration/proof`, they require an EC1 bearer session and current ban checks. Identity comes from the session; body player IDs have no authority. A migration scope can access only readiness and migration operations.

## Snapshot

`PUT /save` accepts `{game:"ec1",schemaVersion:1,playtime,data,expectedSaveVersion,operationId,deviceId?,intent?}`. `data` is a dictionary of strings. `data.CLOUD_ALL_DATA` is the JSON string of the complete EC1 preference dictionary; `data.Playtime` preserves the captured legacy clock. For an intentionally default first profile use `intent:"new_game"`. Unknown preference and envelope-data fields and explicit zero/empty string values survive publication. Credentials, PF/GPGS/backend credential keys, password/token/secret keys are forbidden. Maximum serialized data length is 2,000,000 characters.

The native required set is exported as `nativeKeys` in `src/game/validation.ts`: the historical 60 keys plus 30 supplemental integer keys, six string keys and three float keys, total 99. This closes the original serializer's missing `elysianTaken`, quest task/progress, tutorials, companion settings, step-up offers, costume selection/transmog, daily reset, boosters and local clock. Legacy imports validate the historical 60 keys without fabricating newly introduced entitlements or preferences. Completeness requires key presence; locked characters may legitimately have empty attribute strings.

`gamedata` is a JSON object with nonnegative finite gold/ruby/stageProgress/tutorialProgress/timeCounter and usedCoupons/stageInfo arrays. Character JSON must contain level/exp and four serialized equipment strings. Inventory is the actual EC1 format: three `^` separated groups, each containing `|` separated JSON item objects; initialized empty inventory is `^^`. Consumable is optional empty legacy data or a JSON object. `achievements_new` is empty legacy data or exactly 27 `0|1` flags, **not JSON**. Supplemental integers use signed Int32 bounds; supplemental floats are finite strings.

`GET /save` and successful publication return `{playerId,saveVersion,playtime,data,saveState,operationId}`. No initial snapshot is an expected `404 {error:"no_save",saveState:"native_uninitialized",saveVersion:0}`. `409 save_conflict` means fetch/reconcile while retaining the journal; an operation ID reused with changed bytes/options is `409 operation_id_reused`. Replaying the identical operation returns its exact committed revision, even after later saves. A same-account save cannot decrease published playtime. Admin restoration opts into decrease explicitly and uses the same publication primitive.

Publication writes immutable uniquely named R2 bytes, verifies readback SHA256, then atomically batches D1 revision/operation insertion and a conditional `player.save_version` update. Failed staging never changes the published head. Concurrent writers cannot both publish the same expected version. Unreferenced staged objects are retained for later audited retention handling; no destructive cleanup is included. `save_revision` is the immutable history, and `save_operation` is the exact-retry index. R2 integrity/missing objects fail typed; they do not become empty/new saves.

## Mail, daily and coupons

- `GET /inbox` returns `{mail:[{id,title,body,rewards,createdAt,expiresAt,readAt,claimedAt}]}` (latest 100 unexpired rows).
- `POST /mail/:id/read` returns `{read:true}` and does not claim anything.
- `POST /mail/:id/claim` accepts `{operationId,expectedSaveVersion}` and returns the whole resulting save.
- `GET /time` returns epoch milliseconds `serverTime` and ISO `isoTime`.
- `GET /daily/check` returns `{claimCount,lastClaimAt,nextEligibleAt,eligible,serverTime}` in epoch milliseconds. Attendance retains EC1's elapsed 24-hour rule.
- `POST /daily/claim` accepts `{operationId,expectedSaveVersion}`. Configure `game_config` key `daily_rewards` as `{rewards:[[{id:"gold",amount:100}],...]}`. An unconfigured table is `503 daily_not_configured`. The grant updates LastReward/LastRewardTime and publishes before receipt completion. Daily quest/challenge/booster refresh remains a separate client integration gate; this endpoint does not silently infer those reward/reset codecs.
- `POST /coupon/redeem` accepts `{code,operationId,expectedSaveVersion}`. `coupon` rows must be enabled and unexpired. Case-sensitive codes are 1-64 ASCII letters/digits/underscore/hyphen. The grant updates `gamedata.usedCoupons` and durable redemption together.

Rewards have EC1-compatible `{id,amount,name?,itemCategory?}` shapes. Currently supported: `gold`, `ruby`, and known `costume_{character}_{1..8}` flags. Currency earned counters update when present. Amounts and resulting balances stay within Int32. Inventory item rewards need canonical item database metadata and are deliberately `422 reward_unsupported`; no mail/daily/coupon claim or save is recorded on that error. Pending migrated PlayFab mail stays in the source/archive until its codec is verified; this server never clears it.

All receipts (`grant_receipt`) and mail claimed state publish in the same D1 transaction as the whole save. A lost reply replays the original receipt/save. Multiple claim attempts cannot duplicate the reward. A source can have only one receipt per player. Clients must import/reconcile the returned full save before subsequent uploads; gameplay inventory is still client authoritative and this milestone is not a server authoritative combat/economy implementation.

## Read-only migration

Migration defaults off (`LEGACY_MIGRATION_ENABLED` must equal `true`). New-account/save/grant operations make zero PlayFab calls. The adapter permits only explicit read/authentication endpoints and rejects all update/delete/marker/clear-mail/link/unlink/account-create operations before transport. Configuration/network failures cannot be interpreted as source absence.

`POST /migration/proof {sessionTicket,deviceId?}` revalidates the ticket with PlayFab `Server/AuthenticateSessionTicket`, obtains canonical legacy ID from the response, then reads `Server/GetUserAccountInfo`. It reserves/mints a 15-minute migration session for that canonical ID and stores server-owned `migration_identity_proof` with Google subject/email and a SHA256 CustomID hash. Device context is set only if supplied device ID exactly equals server CustomID. A submitted ID is never ownership proof. Long-term auth linking must additionally verify the same legacy Google subject or a read-only legacy email/password login; Discord/Apple cannot be arbitrarily attached by migration scope.

`POST /migration/import` uses a migration bearer session and `{sessionTicket,operationId,localSnapshot?}`. It revalidates source ownership and reads user data, inventory, profile and account info. Both originals are independently archived into immutable R2 and SHA256 checked before ranking. Source ticket/credentials are never included in archives. A local snapshot can compete only when `localSnapshot.deviceId`, verified session device context and current server CustomID agree. Legacy clients sometimes unlinked CustomID; those cases return `local_owner_mismatch` with preserved originals and require recovery rather than trusting a submitted local ID. Cryptographic local save signing did not exist in the old client; this proves legacy account/device provenance, not that gameplay bytes cannot be edited by their owner.

Validated healthy sources rank by `gamedata.timeCounter`, with cloud winning ties. Separate high Playtime cannot make a reset/default source healthy. Strong progress, upgraded characters, meaningful inventory or entitlements establish health; standalone currency balances do not. Missing/truncated/default sources cannot outrank healthy progress. Both damaged/default sources enter `migration_recovery_required`. Nonempty PlayFab inventory/virtual currency requires `migration_entitlement_review_required` until its entitlement codec is reviewed; archived purchase/inventory evidence is never discarded or silently merged. Legacy ban evidence blocks import.

The imported winner publishes as `imported_pending_auth`; `migration_record` tracks source archives/winner/version independently. Retries after commit return the actual committed save, never rerank or overwrite it. `/migration/complete` requires a normal player scope, an existing durable EC1 identity and a published imported snapshot, then sets migration complete and player migrated. `/readiness` separately reports nativeComplete and migration state. Source archive/save import alone is not native completion. Migration remains disabled for deployment until controlled legacy ownership/device/provider and entitlement tests pass.

SQL schema for admin integration is `migrations/002_game.sql`. Admin restores call exported `publishSnapshot`; all writers use the same CAS/R2 protocol. Save/grant/mail/config timestamps use epoch milliseconds. Authentication session/ban timestamps use epoch seconds as documented by the auth module.
