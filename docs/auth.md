# EC1 player authentication

`src/auth/index.ts` exports the Hono subapp mounted at `/api/auth`, `requirePlayer`, and `mintMigrationSession`. Every native account creation path uses only EC1 D1. Native guest/register/signin/refresh and provider flows make zero PlayFab requests, including failures. The only auth-side PlayFab request is an explicitly noncreating legacy email ownership proof from a migration-scoped session. New players have an `EC1X` ID, `native_uninitialized` state and save version zero; authentication does not require or invent a save.

## Client protocol

- `POST /guest`: `{bootstrapId, bootstrapSecret, deviceId?,deviceCredentialId?,deviceSecret?}`. Generate and persist the bootstrap and native device credential **before** submitting. `operationId` is accepted as a bootstrapId alias. Secrets are random 32-byte base64url (43 characters), not legacy device IDs. Retry exactly these values after a lost response within the 120-second acknowledgment window. The shipped client always sends the device credential; its installation ID is random and distinct from the legacy CustomID.
- `POST /device/login`: `{deviceCredentialId,deviceSecret,deviceId}`. Explicit noncreating sign-in, including after refresh expiry. Unknown credentials return `device_credentials_not_found`; mismatched, revoked or banned credentials fail closed. A guest whose creation acknowledgment was lost can recover with its already persisted device credential without replaying an old creation request.
- `POST /link/device`: Bearer plus the same device fields. Native owners may add another installation; migration scope additionally requires committed import and verified original CustomID ownership. Credentials cannot move between players. Password reset revokes device credentials.
- `POST /register`: same bootstrap fields plus `{email,password}`. Emails are normalized to lowercase. New passwords are 10–256 characters; salted PBKDF2-SHA256 with 100,000 iterations respects the Worker WebCrypto iteration ceiling. Native email recovery is separately configuration gated under `/api/recovery`; registration email verification remains a release gate. Provider linking supplies a second recovery method.
- `POST /login`: `{email,password,deviceId?}`. Unknown identity and incorrect password return `invalid_credentials`; database faults return `auth_unavailable`. There is no implicit creation or migration. Login limits each IP/email pair to 15 attempts per five-minute bucket.
- `POST /refresh`: `{refreshToken,operationId}`. Persist the operation ID with its pending request before sending. Retrying the same predecessor and operation for 120 seconds returns the same successor, provided the successor has not itself been consumed. Different-operation predecessor reuse revokes the session family, including its outstanding access tokens. Do not start concurrent refresh operations.
- `POST /logout`: Bearer authentication; revokes the entire session family.
- `GET /identities`, `GET /readiness`: Bearer authentication. Identity responses omit provider subjects and password metadata. Readiness reports save version/state and the migration feature flag.
- `POST /link/email`: Bearer plus `{email,password}`. A migration-scoped request first requires the server-owned migration_identity_proof row, then proves the supplied email/password using PlayFab Client/LoginWithEmailAddress with CreateAccount:false and a matching canonical player ID. A preexisting legacy password may be shorter than the new-registration minimum; it is retained only after successful proof. Promotes verified migration sessions to a native session after adding the backend credential. It does not itself mark migration complete or change saves.
- `DELETE /identities/:provider`: native Bearer session. Atomic conditional deletion prevents removal of the last durable identity even when two unlink requests race. Guest credentials cannot be unlinked here. Sessions using the removed provider are revoked.

Auth success is `{playerId,accessToken,refreshToken,expiresIn:900,saveState,saveVersion}`. Errors are `{error:string}` with typed 4xx conflicts/auth failures and 503 configuration/infrastructure failures. Bootstrap retries resolve the same profile and initial session only within 120 seconds of creation and while the initial refresh remains unused and valid. Session and refresh publication both require the matching live bootstrap; expiry/cleanup cannot resurrect it. Password reset atomically removes those proofs alongside session/device revocation. After the acknowledgment window, use the persisted refresh or explicit durable account sign-in.

## Providers

First call `POST /provider/:provider/challenge` with `{intent:'signin'|'create'|'link'}`. Link requires a Bearer session. It returns `{challengeId,nonce,state,authorizeUrl?}`; challenges expire after five minutes. Google/Apple SDK requests must use this server nonce. Discord additionally requires `{redirectUri,codeChallenge}` where codeChallenge is SHA256/base64url of a random RFC 7636 verifier. Open the returned authorize URL and retain its state.

Complete `POST /provider/:provider` with `{intent,challengeId,idToken}` for Google/Apple, or `{intent,challengeId,code,codeVerifier,redirectUri,state}` for Discord. Create includes the bootstrap fields; link includes Bearer authentication. Google/Apple RS256 proof validates key ID, signature, exact configured audience, issuer, expiry, issued-at and nonce. Apple token nonce must match the value passed to its SDK; do not hash the server nonce unless that is also the SDK request convention. Discord exchange uses only allowlisted redirects, validates PKCE/state, and resolves the subject from `/users/@me`. Emails and display names never merge accounts.

Signin never creates unknown identities. Create never attaches an existing identity. Link never moves an identity between players. Each player can link at most one identity per provider. From migration scope, Google linking additionally requires exact matching of verified Google sub to game-owned migration_identity_proof.google_subject. Discord/Apple cannot directly promote a legacy session: prove the legacy email or Google identity first, then link additional methods from the native session. Once proof succeeds, the challenge stores the verified subject and a keyed canonical request fingerprint, never the raw provider token/code/password. An identical completion request may retry for 120 seconds (and within the original challenge expiry) without exchanging an already consumed Discord code or repeating provider verification. Create, signin and link retries return the same initial session/refresh credential. Changed request fields or owner fail. After that window obtain a new proof challenge and signin; do not silently create another profile. Email linking likewise replays the same credential/owner request and returns its deterministic initial session; a retry after verified legacy email linking does not call PlayFab again. Verification of an existing owned credential accepts the retained legacy password, including a short password; the new-password minimum applies only when adding a new native identity.

Required configuration: independent `PLAYER_TOKEN_SECRET` (at least 32 characters), comma-separated `GOOGLE_CLIENT_IDS`, `APPLE_CLIENT_IDS`, and `DISCORD_GAME_CLIENT_ID`, `DISCORD_GAME_CLIENT_SECRET`, `DISCORD_GAME_REDIRECT_URIS`. Missing configuration yields `provider_not_configured`, never another provider or PlayFab. `ALLOW_NEW_ACCOUNTS` must be exactly `true` to create. Provider proof fixtures verify protocol logic, but actual provider code/token exchange, SDK nonce behavior, packaged native redirect routing and signed-device Google/Apple validation remain release gates. Production registrations and challenge readiness were checked on 2026-10-23 as recorded below.

## Isolation, bans and migration

Player access JWTs use HS256 with issuer `ec1-backend`, audience `ec1-player`, 15-minute lifetime, session ID and scope. Every authenticated request reads its session and current ban, so logout/reuse/unlink and bans affect existing tokens immediately. Player tokens cannot authorize administrator routes. All auth and `player_ban` timestamps are Unix seconds; a ban is active when revoked_at is NULL and expires_at is NULL or in the future. Other feature tables may use milliseconds; consult their contracts before formatting dates.

Refresh tokens are random or a domain-separated HMAC successor derived from the predecessor and operation. D1 stores only hashes. No raw provider tokens, refresh tokens, passwords, signing keys or bootstrap secrets are persisted. A domain-separated keyed bootstrap fingerprint binds an operation to its create intent and credentials without providing an additional fast password guessing oracle. Transactional D1 batches prevent orphan players on identity/bootstrap uniqueness races.

`mintMigrationSession(env, verifiedLegacyPlayerId, deviceId)` is exclusively for a caller that has already proved legacy ownership with a read-only legacy adapter. It is gated by `LEGACY_MIGRATION_ENABLED==='true'`, retains a validated legacy ID and mints a 15-minute `migration` scope. It creates only a pending EC1 shell. The game module restricts this scope to migration/readiness and requires a durable email/provider identity or active native device credential plus a native player-scoped session before completion. Device completion additionally preserves verified original CustomID ownership. Linking never completes migration; verified save publication/readback remains the game module's responsibility.

### Optional browser broker (deployed 2026-10-23)

Production migration `024_browser_auth.sql` was applied before the 2026-10-23 deployment. Other environments must apply it before using the browser transport. Google, Apple and Discord accept `POST /provider/:provider/challenge` with `{intent,transport:'browser',codeChallenge}`; link additionally requires the owning Bearer session. `codeChallenge` is SHA256/base64url of a per-attempt random 43–128 character RFC 7636 verifier retained only by the client. The returned `authorizeUrl`, `transport:'browser'`, `challengeId`, `state` and `nonce` describe one five-minute attempt. Unknown/unconfigured providers fail explicitly; no provider or account-creation fallback occurs.

Google uses dedicated `GOOGLE_BROWSER_CLIENT_ID`, secret `GOOGLE_BROWSER_CLIENT_SECRET`, and `GOOGLE_BROWSER_REDIRECT_URI` ending `/api/auth/browser/google/callback`. Apple uses a Services ID in `APPLE_BROWSER_CLIENT_ID`, `APPLE_BROWSER_TEAM_ID`, `APPLE_BROWSER_KEY_ID`, secret PEM `APPLE_BROWSER_PRIVATE_KEY`, and `APPLE_BROWSER_REDIRECT_URI` ending `/api/auth/browser/apple/callback`. Both redirect URIs must be fixed HTTPS URLs without query/fragment/userinfo. Apple posts an authorization code using `response_mode=form_post`; the server generates a short-lived ES256 client secret, exchanges the code, then verifies the signed identity token against the exact Services ID audience and challenge nonce. Native Apple/Google proof audiences and SDK paths remain unchanged. Browser credentials do not belong in the Unity app or Git. Discord reuses its existing configured HTTPS `/api/auth/discord/callback`; legacy non-browser challenges retain their existing code bridge behavior.

The server exchanges provider codes and verifies identity before returning only `{state,ticket}` through fixed `gacogames-ec1-bridge://oauth/google|apple|discord`. No provider code, access token or identity token is returned in that URL. Tickets are keyed, short-lived capabilities also bound to the client's PKCE verifier. D1 retains the verified subject and ticket hash, never raw provider credentials, provider codes, client verifier or raw ticket. Google/Discord use a separate server-derived provider PKCE verifier; Apple's supported code flow uses nonce/state and confidential client authentication, while broker redemption independently enforces client PKCE.

Complete the existing `POST /provider/:provider` with `{intent,challengeId,state,ticket,codeVerifier}` plus bootstrap fields for explicit create, or Bearer for explicit link. Existing transactional identity ownership and initial-session retry rules apply: signin never creates, create never merges, and linking never transfers identities. An identical completion can retry for 120 seconds; changing intent/owner/request fails. Callback replay cannot exchange another provider code. Cancellation must discard the active in-memory attempt and never submit completion; callbacks themselves create no account/session.

Desktop clients without a custom-scheme handler may poll `POST /browser/:provider/poll` with `{challengeId,state,codeVerifier}` every two seconds during the active attempt. It returns `{pending:true}`, `{state,ticket}`, or `{state,error}` for cancellation/provider failure. Stop on cancellation, completion or challenge expiry. Polling never creates sessions. Production provider registration, secret installation and deployment are complete. Actual provider code/token exchange, packaged browser handoff, real signed-device validation and Apple revocation/account-deletion lifecycle remain release gates.

Protocol references: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [Apple authorization request](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.), [Apple client secret JWT](https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens), and [OAuth security best practice](https://www.rfc-editor.org/rfc/rfc9700.html).
