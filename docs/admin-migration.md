# Admin migration — October 28, 2026

The Classic workspace follows the existing EC2 migration workflow: open a PlayFab legacy account, select **Migrate to backend**, inspect the source, UID, cloud playtime, original login methods and active bans, then confirm. This does not load or upload device progress. Existing canonical or historical backend saves, completed migrations and in-progress player migrations cannot be overwritten.

`src/admin/migration.ts` owns read-only PlayFab account/data/inventory/ban reads, immutable source archival, preview binding, target-state checks and atomic publication. It converts the latest immutable backend legacy edit when one exists; both that revision and the original live PlayFab source remain archived. `src/migration/legacy-conversion.ts` converts historical positional, preference-dictionary and schema-1 cloud data using Unity's save contract. It has no network, player authentication or local-save dependencies. The authenticated Classic control routes only compose those operations.

The first backup, original UID, durable login mappings, migration provenance, preserved bans, audit and operation receipt publish in one D1 transaction after R2 write/readback checks. Repeating an acknowledged operation returns its receipt; simultaneous migrations cannot create multiple first revisions. Apply `036_admin_classic_migration.sql` before activating the routes. An unsuccessful preview or publication can leave an immutable source archive or staged object, but cannot replace an existing save.

Original Google subjects are linked when available. Existing native passwords and provider mappings are preserved. If the original mailbox has no native email credential, a random password is hashed using EC1's existing PBKDF2 format and encrypted with an EC1-specific AES-GCM key for delivery. Password plaintext never enters audit, receipts or responses. The explicit migration action can request delivery; delivery failures do not roll back the saved backup. Staff can retry pending/failed delivery independently, and password reset or replacement supersedes the queued credential. A successful delivery removes the encrypted payload. A `sending` record after an interrupted delivery requires checking delivery before retrying.

Login conflicts block migration and show the current backend owner for review. Existing Classic account controls remain responsible for reviewed identity moves, email changes, password reset and revision restoration. This action does not automatically displace another account's login. Nonempty external PlayFab inventory/currency or pending legacy mail require review rather than being discarded or issued twice. Empty/damaged cloud saves require recovery. No PlayFab writes occur, including password changes, markers or clearing mail.

Local fixtures use synthetic identities and intercepted outbound requests. Coverage includes historical conversion, source changes, immutable originals, edited legacy revisions, role/origin checks, provider outages, identity conflicts, active bans, staged-storage failures, concurrent publication, transaction rollback on audit failure, exact operation retries, delivery failures/retries and credential supersession. These tests do not migrate real players or prove real inbox delivery.

### Exhausted legacy daily allowances

Legacy preference and positional saves can contain negative exhausted booster quotas or treasure, march and chaos entry counters. Conversion clamps these counters to zero without awarding charges. The booster quota's missing or `-1` marker still means not activated. Other invalid values and negative counters in canonical snapshots remain rejected. Preview and migration audit details include the adjusted fields and original values; the immutable source archive retains the original bytes.

This correction was deployed on November 5, 2026 as EC1 version `54b1af93-26cc-4f14-89bc-ab9f14240875`, replacing only the admin route module. All 216 backend tests, typecheck/build and isolated bundle checks passed. The affected archived source also passed conversion with only its two exhausted daily counters adjusted. No production account was migrated during validation.

## Production rollout

On October 28, 2026, migration 036 was applied and the routes were deployed as EC1 version `e3ddfadd-90ad-4179-a835-011e995683e6`. The shared dashboard was deployed as version `ad5ed06b-0a66-4536-8f45-5ddf233fab7a`. The original live EC1/EC2 server modules, static asset bindings and other environment bindings were preserved byte-for-byte; isolated wrapper modules add only these routes and the rebuilt dashboard application. The dashboard source baseline was reconstructed from its deployed source map and reproduced the deployed JavaScript before the two migration UI changes were applied. The source implementations in the repositories also include the feature for subsequent normal builds.

All 204 backend tests, backend typecheck/build, dashboard build and 43 admin-client assertions passed. The synthetic browser check covered preview and successful completion. Live smoke checks verified enabled recovery on both EC1 domains, the reset page, authenticated migration routes, the exact served dashboard bundle hash and existing EC2 authentication. No production player migration, credential creation or email delivery was performed. Readback evidence and rollback originals are in ignored `.wrangler/classic-migration-release/`.

### Isolated route mount correction

The initial isolated deployment mounted the control subapp at its child paths instead of `/api/classic-admin`, causing authenticated preview requests to return 404 even though anonymous middleware checks passed. `src/admin/migration-entry.ts` now mounts the control app with the same absolute prefix as the normal Worker. The migration integration fixtures import that exact entrypoint. Eight migration tests and typecheck passed, and only the live migration route module was replaced in EC1 version `06f47ca8-2d98-438c-8dfc-12777a3c85c2`. An authenticated production preview was then verified in the existing admin browser session: source details and the confirmation button appeared. No migration or password email was submitted.
