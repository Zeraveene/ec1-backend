## Shared contracts

- `src/env.ts` owns Worker bindings and request context. Auth sets `c.get('player')` to PlayerContext, and exports `requirePlayer` middleware.
- `src/auth/index.ts` exports `createAuthApp()` mounted at `/api/auth`. Owns authentication/session/provider/linking routes and `migrations/001_auth.sql`.
- `src/game/index.ts` exports `createGameApp()` mounted at `/api/game`. Owns whole saves, safe grants, daily/coupons/mail, read-only migration and `migrations/002_game.sql`. Auth middleware applies on the game subapp; migration scopes only reach migration/readiness operations.
- Common player table is `player`: `id TEXT PRIMARY KEY`, `display_name TEXT`, `save_version INTEGER DEFAULT 0`, `playtime REAL DEFAULT 0`, `save_state TEXT DEFAULT 'native_uninitialized'`, `device_id TEXT`, `created_at INTEGER`, `updated_at INTEGER`, `migrated_at INTEGER`. Auth creates it; all save writers conditional on `save_version`.
- Snapshot envelope: `{game:'ec1',schemaVersion:1,playtime:number,data:Record<string,string>,expectedSaveVersion:number,operationId:string,deviceId?:string}`. `data.CLOUD_ALL_DATA` is the full EC1 SaveData.ToJson preference dictionary JSON; `data.Playtime` is legacy captured time. Preserve valid unknown data. Backend session determines player identity.
- Save result: `{playerId,saveVersion,playtime,data,saveState,operationId}` as applicable. Auth result: `{playerId,accessToken,refreshToken,expiresIn,saveState,saveVersion}`. Error: `{error:string,reason?:string,retryAfterSeconds?:number}`.
- Save publication stages R2 immutable bytes/readback and conditionally publishes D1 rows. No claim completes until its save/grant publication succeeds. Operation IDs alone are not authentication.
- `src/admin` and `web` are owned by the coordinating agent. Dashboard has independent admin auth and never receives player/provider secrets. No public setup/admin master key flow.
- Tests use isolated Miniflare D1/R2, synthetic profiles and intercepted outbound calls. Fail tests on any PlayFab mutation or any new-user PlayFab request.
- Root coordinates shared configuration, deployment, integration, and commits. Agents edit only their owned paths and do not commit shared work without coordination.

## Purchase grants and optional login — October 27, 2026

The user authorized production purchasing and checkout without account sign-in. This supersedes the October 22 requirement that purchases require login. Keep the existing purchase feature boundary: `binding.ts` owns stable store-account identifiers, `guest.ts` owns purchase-only capabilities, `receipts.ts`/`store.ts` verify platform proof and state, `catalog.ts` owns reward definitions, and `grants.ts` publishes immutable D1 grants/offer reservations/paid flags atomically. Route composition remains in `purchases/index.ts`. Purchases never publish gameplay snapshots or invoke PlayFab. The old `/claim` save writer stays blocked in manual-backup mode and cannot consume a transaction already issued through the grant API.

Unity `Ec1PurchaseSession` selects the signed-in account when available and compatible with save ownership; otherwise it silently creates a per-save anonymous purchase identity. A save that already has a guest identity keeps it after later backup login, preserving store binding and pending grant ownership. Optional backup authentication is unchanged. Guest identifiers/secrets live only in the encrypted installation-local purchase vault; short-lived tokens exist in memory and use a distinct EC1 purchase token domain. They cannot authenticate game, account, backup, editor-test, or admin routes. Guest creation does not depend on ALLOW_NEW_ACCOUNTS and does not create account identities or save revisions. New guest creation is paused with checkout; existing guests can still renew sessions to recover paid operations.

The local save remains the gameplay authority. Pending guest proofs route to their original save lineage using journaled store bindings. The client verifies the authenticated server grant, commits rewards plus the applied marker in one durable save transaction, then confirms the store and independently acknowledges delivery. Retries return the same immutable grant. Restore grants have a distinct stable ID and no currency/material rewards. One-time offer reservations and global store-token uniqueness prevent duplicate bundle issuance. Legacy base64url purchase keys cannot be claimed again under the new hexadecimal key format.

Production IAP_PURCHASES_ENABLED is enabled; staging remains disabled. Google uses signed proof plus read-only Publisher purchase state. Apple uses the existing pinned-chain StoreKit 2 signed receipt policy; signed revocations and ledger revocations are rejected, but no ongoing refund sweep or current App Store Server API lookup is introduced. Guest credentials are not exported in cloud backups. Reinstall/device replacement cannot recover a guest purchase identity from a gameplay backup alone; historic/unbound or foreign store proof remains pending for support. Store purchases on a signed-in account retain that account binding. Do not claim a store release or a real signed-device payment based on compile/fixture tests.

Official platform references checked October 27, 2026: https://developer.android.com/google/play/billing/integrate and https://developer.apple.com/documentation/storekit/product/purchaseoption/appaccounttoken(_:). Existing Unity IAP 5.0.2 remains installed; no stack or package changes.
