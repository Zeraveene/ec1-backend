# EC1 purchases foundation

`createPurchasesApp()` from `src/purchases/index.ts` mounts at `/api/purchases`. `020_purchases.sql` owns globally unique purchase provenance, per-player store account bindings, and durable paid flags. Native player authentication and current bans apply to every route. Migration credentials cannot claim purchases. The default `IAP_PURCHASES_ENABLED` gate remains false; no real store call, live-player proof, deployment activation or native purchase release is validated by these fixtures.

## Protocol and authority

1. `GET /account-binding` returns `{game:'ec1',googleObfuscatedAccountId,appleAppAccountToken,purchasesEnabled}`. IDs remain stable across retries and are distinct for each EC1 backend player. Before purchase, the client must pass these values to its Google obfuscated account ID / Apple app-account-token purchase option. Store proof must contain the matching authenticated account binding. A historical receipt without this binding enters a support/recovery hold; it cannot automatically regrant historic consumables to a new backend identity.
2. Preserve a pending Unity IAP order and its stable operation ID before sending. Submit `POST /claim` with `{platform:'google'|'apple',productId,expectedSaveVersion,operationId}` and Google `{receiptJson,signatureBase64}` or Apple `{jwsReceipt}`. Receipt JSON must retain its exact original signed bytes. Client price, reward amount, transaction ID or claimed entitlement is never authority. The backend derives product and transaction provenance from verified proof.
3. A successful claim returns the standard full save result plus `{purchaseKey,status:'granted',confirmPurchase:true}`. Commit/readback covers the reward, whole save, grant receipt, purchase ledger transition and paid flags atomically. Only after durable journal/save handling may the client confirm its Unity `PendingOrder`. Failure, missing save, store pending state, timeout and version conflict leave the order unconfirmed.
4. Retry the identical operation after a lost response. The response identifies its original immutable save revision; it is an acknowledgment of that operation, not a claim that the revision is still current. A later signed Google receipt that acquires an order ID resolves the same canonical purchase-token hash. Different operation IDs for an already granted transaction return `409 purchase_already_granted` with `{receipt:{playerId,purchaseKey,saveVersion,operationId},latestSaveVersion}` and **no old save data**. Fetch the current save and reconcile the durable transaction before confirming the store order. Cross-player receipt replay returns `purchase_already_claimed` and transfers nothing.
5. `GET /ledger` lists safe purchase status/revision metadata for the authenticated owner. It does not disclose raw receipts, store purchase tokens, publisher credentials or receipt hashes.

Claims are capped at 30 per edge IP per five-minute window. This is a bounded service safeguard, not a distributed fraud-detection system.

## Verification and independent EC1 configuration

Required flags/bindings:

| Binding | Purpose |
| --- | --- |
| `IAP_PURCHASES_ENABLED` | Exactly `true` allows new claims; defaults disabled |
| `IAP_GOOGLE_PUBLIC_KEY` | EC1 Play Console licensing RSA SPKI base64; public but must be independently verified |
| `IAP_GOOGLE_SERVICE_ACCOUNT` | Worker-secret JSON credential with EC1 Android Publisher read access; no EC2/review credential fallback |
| `IAP_GOOGLE_PACKAGE_NAME` | EC1 package, verified in Unity Editor as `com.gacogames.epiccon` |
| `IAP_APPLE_BUNDLE_ID` | EC1 bundle, verified in Unity Editor as `com.gacogames.epiccon` |
| `IAP_APPLE_VERIFICATION_MODE` | Exactly `receipt` selects signed StoreKit 2 receipt mode; never selected after another verifier fails |
| `IAP_ALLOW_TEST_PURCHASES` | Exactly `true` explicitly allows sandbox/test proof; defaults denied |

Google verifies SHA1withRSA over original `INAPP_PURCHASE_DATA` bytes using the EC1 licensing key, then checks exact package, purchased state, signed product ID and purchase token. The Publisher service-account assertion uses RS256 and the Android Publisher scope. The read-only `purchases/productsv2/tokens/{token}` response must report `PURCHASED`, one matching product, quantity one, valid completion time and matching `obfuscatedExternalAccountId`. Pending/cancelled, another game, wrong account, wrong product, test purchases without opt-in, malformed quantity and store failures grant nothing. No store acknowledgment/consume/refund mutation is made by this backend: Unity confirmation remains the client integration responsibility. The API's fields and pending-state contract are documented by [Google](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.productsv2).

Apple verifies ES256 StoreKit 2 JWS using its certificate chain anchored to the pinned public Apple Root CA G3 in source. The submitted chain cannot replace that trust anchor. The verifier additionally requires the Apple transaction-signing leaf purpose OID, Apple intermediate purpose OID, intermediate CA constraint, certificate validity at signedDate, and a finite signedDate no later than the permitted clock skew. Bundle ID, product, transaction identity, quantity one, account-token UUID, production/sandbox policy and transaction revocation are checked. This improves the copied EC2 baseline's missing certificate purpose/validity checks, following the [official Apple verifier's criteria](https://github.com/apple/app-store-server-library-node/blob/main/jws_verification.ts).

Receipt mode provides proof of signed facts at their signing time. It does not perform OCSP, a current App Store Server API revocation lookup, or a periodic refund sweep. Production activation needs an explicit reconciliation/refund policy and signed-device evidence. Arbitrary legacy base64 App Store blobs and unsigned Xcode/local-testing transactions are not accepted; the client must submit `order.Info.Apple?.jwsRepresentation`.

## Catalogue and grants

Product IDs and quantities come from EC1 `Assets/Scripts/Services/IAPManager.cs` and `Services/OneTimeOffer.cs`, not EC2 SKUs. Ruby packs 1–8 grant 9/32/100/200/400/800/1600/3200 Ruby. Premium, character unlocks, boosters, costume packs and Wyvern costumes write the corresponding durable EC1 flags. Starter grants premium plus 150 Ruby/150,000 Gold once. Step-up 1–5 include the audited EC1 currency, material and consumable bundles; jewel packs use the three matching material grades. Canonical item categories/assets and stack limits are enforced by the game codec. Disabled `date_pack_a`, unknown products, subscriptions, multi-item store orders and quantities other than one are rejected, without confirming the order.

Apple aliases use the actual `iap_*` IDs in the existing iOS build list; Ruby/jewel IDs are shared where the client lists them. Android's current catalogue marks many durable products as store consumables, so server paid flags and transaction uniqueness remain essential. A second distinct paid Starter/Step-up transaction for an already owned one-time offer is held as `purchase_entitlement_already_owned`, requiring support/refund resolution; it cannot duplicate the bundle's currency.

Each transaction reserves its EC1 player ownership only after authentic receipt and store/account validation. An initial-save/publication failure keeps `verified_pending`; no ledger grant or store confirmation is claimed. A successful conditional publication sets ledger `granted`, save version/operation and `purchase_entitlement` rows in the same D1 batch. Every subsequent native save enforces committed paid flags so an offline preference upload cannot erase purchased unlocks. Spending consumable currency/materials remains ordinary gameplay; those balances are not pinned as permanent entitlements.

## Local evidence and release gates

`node --test tests/purchases.test.mjs` uses isolated Miniflare D1/R2, generated synthetic RSA keys, intercepted OAuth/Publisher responses, and a synthetic Apple certificate hierarchy. The Apple trust anchor is replaced **only in the isolated test bundle** using an esbuild loader; production source never accepts a configurable/client-supplied trust anchor. Synthetic private keys live in a checked temporary directory and are removed after tests. The test requires OpenSSL (`C:/Program Files/Git/usr/bin/openssl.exe` on this host).

Coverage includes disabled/untrusted/wrong-game proof, store pending/cancelled/quantity/owner errors, outages, exact-byte signatures, transaction replay with later order IDs, competing players and operations, publication crash/retry, paid flags surviving later saves, Starter/Step-up item quantities, Apple certificate/account/date/bundle/revocation validation, and secret-free ledger responses. Automated tests do not contact PlayFab or real store accounts.

The client delivery adapter uses the installed IAP 5.0.2 extensions: Google `SetObfuscatedAccountId` and Apple `SetAppAccountToken(Guid)` after authenticated account-binding readiness and before checkout. Backend-mode pending orders never enter the old local `AddItem`/`Bought` reward path. `BackendPurchaseProof` preserves Google's exact signed JSON/signature, reads Apple's StoreKit 2 JWS, rejects mixed/quantity-multiple orders, and derives a stable operation ID from the EC1 owner and canonical transaction key. Proofs do not enter the ordinary gameplay journal. The account coordinator owns encrypted retry requests and conditional full-snapshot reconciliation; only its verified same-owner delivery acknowledgment permits `ConfirmPurchase`. Menu retries retain failures, including disabled service, absent initial save, account switches, conflicts and network loss. Synthetic `BackendPurchaseChecks.Run()` covers receipt parsing, canonical transaction retries, account isolation and binding validation without store/network calls.

Before activation: independently verify the EC1 licensing key and service-account permissions; confirm live store catalogue/types and Apple receipt mode policy; prove signed Android/iOS purchase, restart, delayed acknowledgment, multiple devices, canceled/deferred payment, restore and account-switch flows; define refund/revocation and historic unbound-receipt support handling. Keep the server feature flag disabled until those gates pass. The IAP skill audit also found `IAPProductCatalog.json` enabling codeless auto-init alongside the scripted StoreController; the Unity agent is removing that initialization race. Native account-binding API signatures were checked against installed package source; device branches remain release gates until native builds and signed store evidence succeed.
