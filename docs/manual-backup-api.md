# Canonical manual backup local milestone — 2026-10-22

Current deployment, 2026-10-23: Worker `4e5a339d-616f-4f11-864f-0da4cea95497` enables canonical manual backups and one-time legacy cutover, with migrations `026` and `027` applied. New-account creation, recovery and purchases remain disabled. The earlier readiness snapshot below is historical. All 127 backend tests and the build pass. Desktop Google sign-in, empty legacy-account cutover, repeated native sign-in and authenticated latest-backup reads were verified live in the Editor. Local progress and PlayFab originals were not changed.

Legacy sign-in tries native accounts first. A verified missing email/Google identity can receive a restricted migration response (`migrationRequired:true`, `scope:"migration"`). `POST /api/game/migration/classic/source` archives immutable original user data and returns the raw cloud save and source hash. The client converts it without consulting local progress; `POST /api/game/migration/classic/import` publishes canonical revision 1 once. `POST /api/auth/migration/classic/finalize` verifies stored bytes, atomically links the proven identity, marks completion and returns the native session. An exactly empty archived `Data:{}` uses `hasCloudSave:false` and skips publication; the player's first backup remains manual. Malformed/missing nonempty sources never become empty profiles. Subsequent native sign-ins make no PlayFab calls.

All routes below require an EC1 player bearer session. Migration scope is rejected. Account identity comes exclusively from that session; there is no device ownership check. Sign-in does not invoke these routes or publish progress.

- `GET /api/game/backups/latest`: `{playerId,exists:false,revision:0}` for an empty account, otherwise revision metadata.
- `GET /api/game/backups/revisions/:revision`: selected account-scoped immutable revision metadata plus `snapshotJson`, the exact uploaded canonical JSON string. Missing selected revisions return `backup_not_found` (404).
- `PUT /api/game/backups/latest`: `{game:"ec1",schemaVersion:1,expectedRevision:0,operationId:"unique-operation",snapshotJson:"<full GameSaveRecord JSON>"}`. Returns committed revision metadata. No separate player/device identifiers are accepted as identity.

Revision metadata is `{playerId,exists:true,revision,playtime,schemaVersion,sha256,bytes,createdAt,operationId}`. `createdAt` is epoch milliseconds; SHA-256 and byte count describe uncompressed UTF-8 `snapshotJson`. Playtime comes from `progress.timeCounter`, not ancillary `profile.playtime`. Lower playtime is accepted; warning/confirmation belongs to the explicit client action. Server never ranks sources.

The 2 MB uncompressed snapshot limit and 64 container-depth limit precede structural validation. Only uncompressed JSON transport is supported. Full required field/type shape mirrors the current Unity schema 1 using `canonical-schema.json`, generated by `python3 scripts/generate-canonical-schema.py` from sibling `SaveRecords.cs` and `InventorySaveRecord.cs`. Unknown gameplay fields are retained in the original bytes; duplicate JSON properties, credential-like keys, nonfinite/out-of-range numeric types and incomplete section shape are rejected. Catalog hydration and Unity's semantic import validation remain client responsibilities; schema parity and complete source-preservation fixtures must be verified before activation. Do not claim every historical release is supported by these synthetic tests.

`migrations/023_manual_backups.sql` creates independent canonical tables. Publication stages a fresh unique R2 key, verifies its hash, then commits a conditional revision insert and head update in one D1 batch. Both player/revision and player/operation are unique. Retrying identical bytes with the same expected revision/operation returns the original result even after the head advances. Changing those bytes with the same operation returns `operation_id_reused` (409). Stale expected revision returns `revision_conflict` (409). Storage failures return typed 503 errors; no account-not-found inference is made. Failed staging/races can leave unreferenced immutable R2 objects; no cleanup is activated.

Historical preference-dictionary `/save` storage remains separate. In manual-backup mode its writes, gameplay grant writers and migration import/completion are disabled; GET compatibility routes still expose historical data for old clients only. The canonical backup client must use `/backups`. IAP `/claim` is disabled in manual mode because the existing delivery implementation publishes a gameplay snapshot. Independent durable purchase delivery/grant receipts and client acknowledgement are a future milestone; enabling the manual-backup flag does not enable purchases. Admin revision tools select canonical backups with `?format=canonical` on their existing list/get/preview/restore endpoints. Legacy format remains the default for compatibility; unknown formats are rejected. Canonical metadata is also returned as `canonicalBackups` in private workspace player detail. Existing central role and CSRF protections apply; only internal roles export/restore. Verified exports append a metadata-only audit event. Canonical restores require the actor-bound preview hash, expected current revision and idempotency operation ID, stage exact source bytes under a fresh key, and append a new canonical revision/head plus audit in one transaction. Original and current objects remain immutable. The admin selector UI must pass the explicit format to prevent mixing revision families.
